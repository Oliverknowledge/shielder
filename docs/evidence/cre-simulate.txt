Three runs, in the order they happened. Every one shows the same TEE banner
("Trigger requested TEE Execution … AWS Nitro in us-west-2") and every
evaluation line is printed from inside the confidential handler.

RUN 1  evm-dry-settings (deliver:false). The vault had released $5 to its
       registered Hyperliquid account and $1 had come back, but the venue's own
       fills showed no settled loss, so the enclave correctly found nothing to
       attest: realisedLoss24h=0, triggered=false. No signature was produced.
RUN 2  evm-settings (deliver:true), after the trading account realised a
       $7.12 loss on Hyperliquid testnet (two BTC round trips, fees and
       spread; scripts/hyperevm-losing-trade.ts). The enclave read the venue's
       fills, found realisedLoss24h=7119301 ≥ trigger=3000000, signed the
       EIP-712 verdict with the key it holds as a secret, and Shield's relayer
       landed it: tx 0xa02e2fcbe8770f58cb227dc0627ce32e65ca48ac6dee041b579012302d0bf9e4.
       On-chain result: RiskVerdictApplied(nonce=1, realizedLossUsdc=7119301,
       extended=true), cooldownUntil=1788818471, cooldownReason=2 (RISK_VERDICT).
       A top-up simulated against the vault now reverts CooldownActive().
RUN 3  evm-settings with the verifier secret replaced by 0xdeadbeef. The
       workflow dies before any HTTP call, which is what proves the secret is
       load-bearing rather than merely present.

The simulator is not real hardware; its own banner says so. Nothing here
claims an attested enclave ran. Reproduce from the repository root with
`bun run server:evm` running:

  cre workflow simulate shield-risk --target evm-dry-settings --non-interactive \
    --trigger-index 0 --http-payload '{"vault":"0x751D1e26d79FeffE95F8a8662aB7A022780ED023"}' \
    -R cre -e cre/.env

(Nonce 1 is now consumed on this vault: a fresh loss is needed before the
delivering target signs again.)
